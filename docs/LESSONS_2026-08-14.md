# 2026-08-14 — lessons / regressions found

This note records reusable engineering lessons discovered while moving Rozkalns Control from the public fixture UI toward the Phase 2 live read-only GitHub dashboard.

It supplements the current roadmap checkpoint and the individual issues/PRs. It is intentionally historical: it records what failed or was found, why it mattered, and the permanent guardrail that followed.

Baseline when this note was opened: `main=907f32a2992882106f2827832f39369c8e4ffbbc`.

## 1. Cloudflare deployment inventory is ordered history, not singleton state

**Observed regression**

During Gate A, the Worker/UI deployment itself succeeded, but postverify stopped because the verifier required the complete Cloudflare deployment list to contain exactly one record. The account legitimately contained an older historical deployment as well as the new active deployment.

**Root cause**

The verifier conflated deployment history with current traffic state.

**Lesson**

Read the ordered deployment history, select the latest/active deployment, and validate that deployment's traffic assignment. Do not require historical inventory to have length one.

**Permanent guardrail**

Issue #95 / PR #96 now require:

- non-empty deployment history;
- the latest deployment as the active observation;
- exactly one active Worker version in that deployment;
- exactly `100%` traffic to that version;
- fail-closed behavior for split traffic, empty history or malformed evidence.

A write authorization consumed before the postverify failure must not be replayed. Read-only reconciliation comes first.

## 2. First-rollout gates are state-specific and must not be weakened for later states

**Observed constraint**

The original first public UI deploy gate deliberately required the Custom Domain to be absent. After `control.rozkalns.net` was attached, that gate became invalid for routine redeploys by design.

**Lesson**

A one-shot bootstrap gate should remain an immutable historical contract. Do not broaden it simply because production has moved to a later state.

**Permanent guardrail**

Issue #99 / PR #100 introduced a separate existing-domain redeploy gate bound to:

- exact `main`;
- exact successful main CI;
- exact current Worker version;
- exact current deployment;
- exact existing Custom Domain id;
- unchanged routing before and after the deploy.

The sole intended write remains the strict Worker deploy.

## 3. Mobile polish must not weaken safety wording or touch-target contracts

**Observed regression**

The first PR #98 CI run (#187 / `31823155323`) failed two UI contract tests. The polish had:

1. replaced the explicit safety phrase `No GitHub action can execute` with the weaker `Actions disabled`;
2. reduced `.action-button` minimum height from the established `52px` contract to `46px`.

Typecheck and lint were already green; unit tests caught the product-contract regressions.

**Lesson**

Visual compactness is not allowed to silently weaken a safety statement or an established mobile interaction contract.

**Permanent guardrail**

PR #98 restored the explicit safety phrase and the 52px mobile touch target. The normal CI suite keeps both contracts pinned.

## 4. CSS source order is part of the responsive behavior

**Observed regression risk**

While fixing PR #98, `compact-phone.css` was found to load after the main stylesheet. Its older overrides could undo the new A55 hierarchy even when the primary stylesheet looked correct in isolation, including action layout and fixture-badge behavior.

**Lesson**

Responsive changes must be reviewed across the complete cascade, including later device/profile stylesheets. Looking only at the primary CSS file is insufficient.

**Permanent guardrail**

The compact-phone overrides were updated together with the main mobile rules, and source-boundary/mobile regression tests cover the intended A55-class result.

## 5. Strict TypeScript failures are useful contract signals; fix the smallest thing

**Observed regression**

The first live-dashboard CI run for #102 stopped at typecheck because `observedWorkflowState()` accepted a `pull` parameter that was not used under `noUnusedParameters`.

**Lesson**

Treat strict compiler output as an early design-cleanliness gate, not as something to suppress. When behavior is already correct, fix the smallest type/signature mismatch instead of weakening compiler settings or changing unrelated logic.

**Permanent guardrail**

The unused parameter/call-site was removed without changing dashboard classification behavior, and the final exact-head CI passed.

## 6. SPA fallback must never own the API namespace

**Observed integration risk**

Once the live dashboard route existed, `/api/*` had to be guaranteed to reach the Worker rather than being swallowed by static-asset/SPA fallback behavior.

**Lesson**

A control-plane API namespace needs deterministic Worker-first routing. A successful HTML SPA response is not an acceptable substitute for an API response.

**Permanent guardrail**

PR #106 pins Worker-first routing for `/api/*` and requires the expected JSON media-type boundary before parsing control-plane/canary responses.

## 7. Production canaries must authenticate through the same Cloudflare Access boundary

**Observed integration constraint**

`control.rozkalns.net` is protected by Cloudflare Access. An unauthenticated external fetch can hit the Access boundary rather than the Worker, so it cannot authoritatively verify the dashboard runtime.

**Lesson**

Do not create a bypass, public API exception or broader Service Auth policy just to make deployment verification convenient. Authenticate the operator canary through the existing protection boundary.

**Permanent guardrail**

PR #109 uses an operator-provided Access user token only in the `cf-access-token` header, keeps the existing Access policy unchanged, and scrubs the token from child-process environments. Access-token exposure is treated as credential compromise, not harmless logging.

## 8. A prewrite canary must exist on the currently deployed version

**Observed regression**

The first live-read rollout design tried to use `/api/github/dashboard` as a prewrite fixture-mode canary. The currently deployed fixture Worker predated the source change that introduced that route, so requiring the future endpoint before the deploy was not a valid compatibility assumption.

**Lesson**

Prewrite verification must use a stable endpoint already guaranteed to exist on the current runtime. New functionality should be verified only after the version that introduces it has been deployed.

**Permanent guardrail**

PR #111 separates the canaries:

- prewrite: Access-authenticated `GET /api/health` with the stable health contract;
- runtime fixture/live state: proven independently from the active Worker binding;
- postdeploy: Access-authenticated `GET /api/github/dashboard` with the normalized live-read contract.

## 9. Source target is not production state

**Observed state split**

After PR #104, source configuration targets `CONTROL_LIVE_READ_ENABLED="true"`, while the last directly proven production Worker in this work still had the binding set to `false`.

**Lesson**

A merge proves source state. It does not prove Cloudflare runtime state. The same applies to Worker version, deployment id, routing and bindings.

**Permanent guardrail**

Every merge is classified separately as `Production deploy: YES/NO`. A live transition requires a fresh owner authorization bound to exact source/CI and fresh remote observations, followed by postdeploy reconciliation.

## 10. Crossing a production write boundary consumes the authorization

**Observed operational rule**

A deployment can succeed while a later verification step fails. Re-running the same one-shot command after `DEPLOY_STARTED=YES` could perform a second mutation and destroy the ability to reason about the first outcome.

**Lesson**

After the write marker, uncertainty is resolved by read-only reconciliation, never by a blind retry.

**Permanent guardrail**

Production gates emit explicit markers such as:

- `DEPLOY_STARTED=YES`;
- `AUTHORIZATION_CONSUMED=YES`;
- `NO_BLIND_RETRY_IF_STOP_AFTER_DEPLOY_STARTED=YES`.

The authorization is single-use once the write boundary is crossed.

## 11. Fresh-main reconciliation is mandatory under parallel work

**Observed workflow regression risk**

While the current roadmap update was being prepared, parallel work advanced `main` through additional live-read hardening. A roadmap branch prepared from the earlier state would have become stale immediately.

**Lesson**

Chat memory, an earlier PR base and even a recently read SHA are not authoritative once parallel work is possible. Documentation about operational state needs the same freshness discipline as code.

**Permanent guardrail**

Before branch creation, Ready, merge and production authorization:

- fresh-read `main`;
- bind the exact PR head/base;
- bind the exact successful CI run;
- inspect mergeability and unresolved review threads;
- rebase/recreate from fresh main when the intended statement would otherwise be stale.

## 12. Incomplete branch-policy evidence must never become `MERGE_READY`

**Observed design constraint**

Metadata-only active-rules evidence does not prove every possible branch-protection requirement. Checks can be green and GitHub can report `MERGEABLE/CLEAN` while policy provenance remains incomplete.

**Lesson**

Absence of observed blockers is not equivalent to authoritative readiness.

**Permanent guardrail**

The Phase 2 observational dashboard is intentionally conservative:

- observed CI failure → `CI_FAILED`;
- effective changes-requested review → `NEEDS_ANDRIS`;
- running, missing, ambiguous or incomplete policy evidence → `WAITING`;
- CI pass + `MERGEABLE/CLEAN` without complete policy evidence → still `WAITING`;
- the observational live dashboard does not fabricate `MERGE_READY`.

## 13. Final tree/diff matters more than intermediate commit noise

**Observed documentation-workflow mistake**

During the roadmap reconciliation branch, a temporary marker/no-op artifact was created and then removed before Ready. The squash history can still retain intermediate commit-message noise even though the final tree is clean.

**Lesson**

Review the final changed-file set and final content, not only branch commit messages. Temporary diagnostic artifacts must be removed before Ready.

**Permanent guardrail**

The Ready gate includes a fresh final diff/file-scope inspection. A docs-only task must end with a docs-only final tree even if intermediate branch history was messy.

## What these lessons change going forward

The permanent operating model is:

1. exact source identity before every privileged gate;
2. exact remote identity before every production write;
3. separate gates for materially different production states;
4. no silent weakening of safety/accessibility contracts for UI polish;
5. explicit Worker/API routing and authenticated production canaries;
6. stable-current-runtime checks before writes, new-feature checks after deploy;
7. source state and production state recorded separately;
8. consumed write authorization is never replayed blindly;
9. incomplete evidence fails closed;
10. final diff and fresh `main` are authoritative, not chat memory or intermediate branch history.
